## 工作流程
1. A 把用户意图整理成目标、范围、优先级和可核对的完成条件。
2. A 为任务确定唯一 B 负责人，传递工作包，保持用户沟通入口清楚。
3. B 确定依赖、执行边界和写入目录，给 C 派发；必要时建立子任务。
4. C 提交实际改动、产物路径、验证结果、剩余问题和下一步。
5. B 检查证据，必要时自行核验；未达条件继续修复，超出目标或需要关键取舍时上报 A。
6. A 更新台账，向用户提供结果或具体决策问题。用户体验和方向判断由用户保留。

小任务可由同一 AI 承担多个职责，但必须明确执行与验收分别依据什么证据，不能伪称已有独立验收人。

## 先调研，再实现
每项新增能力先查看现有 SDK 与工具、搜索 GitHub、核对官方文档。B 在工作包记录候选与链接、可复用范围、选择理由和自建边界；C 据此实施。尤其 Harness 的会话持久化、上下文管理、恢复及交互测试，要先查当前 PI SDK 和已有测试工具能否承担。选择时核对许可证、维护、版本兼容与依赖成本；不为复用而堆叠零碎依赖，不为新要求推倒有效工作。

用户可能直接询问工程实现以学习，工程师可直接解释；范围与优先级变化须同步 A，避免与总台账脱节。

## 工作包必须包含
任务 ID、用户授权来源与范围、目标、排除项、验收条件、优先级、唯一负责人、A/B/C 聊天或子代理 ID、工作目录与分支、相关文件、已有证据、需要回报给谁、停止条件、恢复入口。

授权来源为：用户于 2026-10-09 在 A 聊天要求实施本项目管理政策，并明确希望只与总办秘书对接、允许组织下层会话。传递可访问的直接用户授权证据；收件方仍遵守其工具的授权校验，不把转述视为扩大权限。

## 台账规则
状态使用：待安排、进行中、待验收、需用户决策、已完成、已暂停。工具运行结束只作为事件记录。

当前状态写在 TASKS.md，每次更新覆盖该任务当前字段；历史过程和报告留在相关证据中。总办秘书维护总台账，B 维护各自工作包并向 A 提交状态更新，避免冲突。

需用户决策时，写明问题、已知证据、可选方案、影响及建议。技术实现与范围内修复由 AI 自行处理。

## 汇报方式
默认顺序：目前结果 → 最大卡点 → 下一步 → 需要用户决定的事项（若有）。用几句话即可；不要用大量日志、文件名、内部术语占据用户注意力。只有有意义进展、失败、交付或决策需求时主动报告。

## 执行能力与恢复
当前 A 环境提供跨聊天读取、创建、发送消息、等待结果及子代理工具；其他聊天必须自行检查。具备工具不等于已经启动任务或永久后台运行。

运行中的任务可等待并接续。结束当前回合后的持续跟进必须配置实际唤醒机制，其状态登记在 TASKS.md。A 负责跟进 B，B 负责 C 的执行与验收；不依赖聊天永久运行。恢复时读取台账、工作包、相关聊天和实际文件后续派，不让用户搬运消息。

源码和管理文档纳入 Git；依赖、构建包、用户工作区、测试临时数据、密钥不纳入。提交采用明确文件清单，上传前核对敏感信息和远端状态，不覆盖远端历史。
